mxApi
=====

Единая точка входа публичного API для MODX Revolution 2.

Пакет даёт транспорт, аутентификацию по bearer-токенам, реестр эндпоинтов,
каталог и выгрузку OpenAPI. Сами эндпоинты поставляют провайдеры — ядро mxApi,
другие пакеты или код конкретного сайта.

Полная документация: https://docs.modx.pro/components/mxapi


Что внутри
----------

- Маршруты под собственным префиксом (по умолчанию /mxapi/v1), не пересекающиеся
  с маршрутами сайта и других пакетов.
- Bearer-токены двух видов: по логину/паролю пользователя MODX и по паре
  client_id/client_secret машинного клиента. В базе хранится только sha256-хэш
  токена, отзыв мгновенный.
- Права: каждый эндпоинт объявляет свой scope и право MODX (mxapi_*), проверка
  идёт штатным механизмом политик на namespace mxapi.
- Реестр эндпоинтов с метаданными: он же источник для каталога в админке и для
  выгрузки OpenAPI. Статических YAML-файлов, живущих отдельно от кода, нет.
- Ограничение частоты запросов, идемпотентность изменяющих вызовов, журнал
  обращений: кто, когда, каким токеном, в каком контексте и с каким результатом.


Требования
----------

- MODX Revolution 2.x
- PHP 7.2+
- Пакет везёт собственный vendor/ (composer, PSR-4). При сборке из исходников
  выполнить в core/components/mxapi/: composer install --no-dev


================================================================================
ПОРЯДОК РАБОТЫ
================================================================================

Шаг 1. Установка
----------------

Установить пакет менеджером пакетов MODX. При установке создаются:

- таблицы modx_mxapi_client, modx_mxapi_token, modx_mxapi_log (при удалении
  пакета НЕ дропаются: в них боевые учётки и аудит);
- системные настройки mxapi.*;
- шаблон политики mxapiTemplate и политика mxapiDefault (группам не назначаются
  — это делается вручную, см. шаг 3);
- пункт меню «Компоненты → mxApi».


Шаг 2. Маршрутизация на веб-сервере
-----------------------------------

Публичный префикс маршрутов задаётся настройкой mxapi.route_prefix, по умолчанию
/mxapi/v1. Запросы с этим префиксом нужно направить в точку входа пакета
assets/components/mxapi/index.php.

--- nginx ---

    location ^~ /mxapi/ {
        try_files $uri /assets/components/mxapi/index.php$is_args$args;
    }

Блок размещается до общего location / сайта.

--- Apache ---

Правила добавляются в .htaccess в корне сайта ВЫШЕ штатных правил MODX (тех, что
заканчиваются перенаправлением на index.php): иначе MODX перехватит запрос
раньше и ответит страницей 404 сайта.

    RewriteEngine On

    # Заголовок Authorization до PHP: при mod_php и CGI Apache его не передаёт,
    # и bearer-токен теряется. mxApi читает REDIRECT_HTTP_AUTHORIZATION.
    RewriteRule ^mxapi/ - [E=HTTP_AUTHORIZATION:%{HTTP:Authorization}]

    # Собственно маршрутизация префикса в точку входа пакета.
    RewriteRule ^mxapi/(.*)$ assets/components/mxapi/index.php [QSA,L]

Если сайт живёт в подкаталоге, в этом же файле должен быть раскомментирован и
приведён к нужному пути RewriteBase (например RewriteBase /shop/).

Если mxapi.route_prefix изменён, в обоих правилах меняется первый сегмент пути:
для префикса /api/mx/v1 — ^api/mx/.

Вместо строки с E=HTTP_AUTHORIZATION на Apache 2.4.13+ с PHP-FPM или CGI можно
включить передачу заголовка директивой в конфигурации сервера или в том же
.htaccess (если разрешено AllowOverride):

    CGIPassAuth On

Достаточно одного из двух способов. Проверить, что заголовок доходит, проще
всего вызовом любого эндпоинта с токеном: ответ token_required при заведомо
верном токене означает, что Authorization до PHP не добрался.

--- Без правки конфигурации веб-сервера ---

Тот же API доступен напрямую, маршрут передаётся параметром route:

    /assets/components/mxapi/index.php?route=/auth/token

Способ рабочий и удобен для проверки установки, но публичным контрактом
считается префикс: интегратору сообщается адрес вида
https://site.ru/mxapi/v1/...


Шаг 3. Права доступа в MODX
---------------------------

API выполняет запросы от имени реального пользователя MODX и проверяет его права
штатным механизмом. Поэтому доступ выдаётся так:

1. Завести пользователя интеграции (или взять существующего) и включить его в
   группу пользователей.
2. Access Controls → Namespace Access: namespace mxapi, политика mxapiDefault
   (или своя на базе шаблона mxapiTemplate).
3. Проверить authority роли участника группы: если запись доступа выдана с
   authority 0, а пользователь состоит в группе с ролью меньшего уровня, он
   получит отказ — и выглядеть это будет как проблема прав mxApi.

Права, которые создаёт сам пакет:

    load               обязательное право namespace (см. предупреждение ниже)
    mxapi_auth_token   выпуск токенов
    mxapi_auth_revoke  отзыв токенов
    mxapi_meta_read    чтение каталога эндпоинтов и OpenAPI

Эндпоинты из других пакетов приносят свои права mxapi_*.

ВНИМАНИЕ. В любой политике для namespace mxapi обязано быть право load: MODX
требует его при загрузке самого объекта namespace, ещё до проверки права
эндпоинта. Без load пользователь получает отказ при полностью корректных
остальных правах.


Шаг 4. Получение токена
-----------------------

Все запросы к API, кроме самой выдачи токена, требуют заголовок

    Authorization: Bearer <token>

Токен выдаёт эндпоинт POST /auth/token. Способа два, и выбираются они параметром
grant_type.

Общее для обоих способов:

- параметр scope обязателен. Это список запрашиваемых scope через пробел
  (meta.read, orders.read и т.д.); какие есть на конкретном сайте — видно в
  каталоге эндпоинтов (шаг 6);
- у пользователя, от имени которого выдаётся токен, должно быть право
  mxapi_auth_token и права всех запрашиваемых scope. Выдать токен шире прав
  пользователя нельзя;
- ответ содержит открытый токен ровно один раз: в базе лежит только его хэш.


4.1. Способ первый: логин и пароль (grant_type=password)
--------------------------------------------------------

Токен выпускается по учётным данным пользователя MODX. Ничего заводить заранее
не нужно.

    curl -X POST 'https://site.ru/mxapi/v1/auth/token' \
      -H 'Content-Type: application/json' \
      -d '{
            "grant_type": "password",
            "username": "api_user",
            "password": "********",
            "scope": "meta.read"
          }'

grant_type можно не передавать — password подразумевается по умолчанию.

Когда уместен: ручная проверка, отладка, разовые вызовы, сценарии, где пароль
вводит живой человек.

Ограничения этого способа:

- вызывающая система вынуждена хранить пароль живого пользователя MODX, а смена
  пароля ломает интеграцию;
- клиента у такого токена нет, поэтому не работают ни собственное время жизни,
  ни IP-фильтр, ни свой лимит частоты, ни allow-list контекстов: TTL берётся
  общий (mxapi.token_ttl), ограничен токен только правами самого пользователя.


4.2. Способ второй: клиент интеграции (grant_type=client_credentials)
---------------------------------------------------------------------

Предпочтительный способ для машинных интеграций: пароль пользователя вызывающей
системе не передаётся, а доступ можно отключить или перевыпустить, не трогая
учётную запись.

Сначала заводится клиент — в админке, на странице правки пользователя, от чьего
имени будет работать интеграция:

1. Пользователи → нужный пользователь → вкладка «mxApi».
   (Вкладка видна тем, у кого есть право save_user: кто может сменить
   пользователю пароль, тот и так выпустит токен от его имени.)
2. Кнопка «Добавить». В окне указываются:
   - название клиента — для людей, видно в списке и журнале;
   - scope — деревом по источникам: всё, весь источник или поштучно.
     Предлагаются только те scope, на которые есть права у ЭТОГО пользователя;
   - время жизни токена: как на сайте (значение mxapi.token_ttl), бессрочно
     либо своё значение в секундах.
3. После сохранения показываются client_key и client_secret. Секрет
   отображается ОДИН раз и в базе не хранится (только хэш). Не скопировали —
   остаётся перевыпуск.

В строке клиента доступны: изменение, перевыпуск секрета (с необязательным
отзывом уже выданных токенов), включение/отключение и удаление. Отключённый
клиент немедленно перестаёт работать — вместе со всеми выданными ему токенами.

Выпуск токена:

    curl -X POST 'https://site.ru/mxapi/v1/auth/token' \
      -H 'Content-Type: application/json' \
      -d '{
            "grant_type": "client_credentials",
            "client_id": "<client_key>",
            "client_secret": "<client_secret>",
            "scope": "meta.read orders.read"
          }'

Обратите внимание: в запросе поле называется client_id, а в админке оно
показано как client_key — это одно и то же значение.

Поля клиента, доступные только правкой в базе (в форме админки их нет):

    allowed_ips   белый список адресов и подсетей; пусто — без ограничений.
                  Проверяется и при выпуске токена, и при каждом вызове
    contexts      контексты MODX, разрешённые клиенту. Пусто — только контекст
                  по умолчанию (mxapi.context), "*" — любой
    rate_limit    свой лимит запросов в минуту; 0 — общий (mxapi.rate_limit_per_minute)


4.3. Что возвращает выдача токена
---------------------------------

    {
      "success": true,
      "data": {
        "access_token": "DfT2...",
        "token_type": "Bearer",
        "expires_in": 86400,
        "expires_at": "2026-07-31T09:00:00+00:00",
        "scope": "meta.read orders.read",
        "user": {...}
      }
    }

expires_in = 0 и expires_at = null означают бессрочный токен: такой выдаётся
только клиенту, которому это разрешено явно (время жизни «бессрочно»).

Токен короче 60 секунд не выдаётся: он не пережил бы собственную выдачу.


Шаг 5. Вызов эндпоинтов
-----------------------

    curl 'https://site.ru/mxapi/v1/meta/endpoints' \
      -H 'Authorization: Bearer <token>'

Заголовки, которые понимает API:

    Authorization: Bearer <token>   обязателен везде, кроме /auth/token
    Content-Type: application/json  для тела запроса в JSON
    Idempotency-Key: <строка>       для изменяющих запросов: повтор с тем же
                                    ключом вернёт ответ первого успешного
                                    вызова и заголовок Idempotency-Replayed:
                                    true, операция заново не выполнится.
                                    Ответ берётся из журнала, поэтому
                                    потоковые ответы и тела больше 256 КБ не
                                    повторяются — такой запрос выполнится
                                    заново
    X-MxApi-Actor: <кто>            кто инициировал вызов на стороне вызывающей
                                    системы; пишется в журнал
    X-MxApi-Context: <ключ>         контекст MODX для эндпоинтов, которые это
                                    допускают; работает только при включённой
                                    настройке mxapi.allow_request_context

Заголовки ответа при ограничении частоты: X-RateLimit-Limit, X-RateLimit-Remaining,
X-RateLimit-Reset. При превышении — HTTP 429 и код rate_limited.

Списочные эндпоинты принимают limit и offset и возвращают meta.total; limit
удерживается в границах mxapi.max_limit.


Шаг 6. Каталог эндпоинтов и OpenAPI
-----------------------------------

Что именно доступно на конкретном сайте, смотрят тремя способами:

- админка: Компоненты → mxApi. Маршрут, методы, scope, право, параметры, пример
  curl, источник (ядро/пакет/проект) и кнопка выгрузки OpenAPI;
- API: GET /meta/endpoints (scope meta.read);
- API: GET /meta/openapi — спецификация OpenAPI 3.0, собранная из живого
  реестра. Файл можно передать интегратору или загрузить в Swagger UI/Postman.

Служебные эндпоинты в каталог и OpenAPI не попадают никогда. Остальное зависит
от настройки mxapi.catalog_filter:

    all         весь публичный контракт сайта (по умолчанию) — каталог работает
                как документация
    scope       только то, что можно вызвать предъявленным токеном
    permission  только то, на что у пользователя есть право MODX

Активный режим возвращается в meta.filter, чтобы короткий каталог не выглядел
как «эндпоинтов нет».


Шаг 7. Отзыв токена
-------------------

    curl -X POST 'https://site.ru/mxapi/v1/auth/revoke' \
      -H 'Authorization: Bearer <token>'

Отзывается именно тот токен, которым выполнен запрос (право mxapi_auth_revoke).
Чужие токены через API не отзываются: для этого есть перевыпуск секрета клиента
с отзывом выданных токенов и отключение клиента в админке.


================================================================================
СПРАВОЧНИК
================================================================================

Формат ответа
-------------

Успех:

    {"success": true, "data": {...}, "meta": {...}}

Ошибка:

    {"success": false, "error": {"code": "invalid_scope", "message": "...",
     "details": {...}}}

Код ошибки (error.code) — часть публичного контракта, на него и следует
опираться в вызывающей системе; текст сообщения может меняться.


Коды ошибок
-----------

    HTTP  Код                      Когда
    ----  -----------------------  --------------------------------------------
    400   invalid_json             тело запроса не JSON-объект
    400   missing_parameter        не передан обязательный параметр
    400   invalid_parameter        параметр не проходит проверку типа/значения
    400   invalid_scope            запрошен scope, которого нет ни у одного
                                   эндпоинта
    400   unknown_context          контекст MODX не найден или недоступен
    401   token_required           нет заголовка Authorization: Bearer
    401   invalid_token            токен не найден (или клиент отключён)
    401   token_expired            срок действия истёк
    401   token_revoked            токен отозван
    401   credentials_required     не переданы учётные данные при выдаче токена
    401   invalid_credentials      неверный логин/пароль или client_id/secret
    403   insufficient_scope       у токена нет нужного scope
    403   insufficient_permission  у пользователя нет права MODX
    403   user_inactive            пользователь неактивен или заблокирован
    403   ip_not_allowed           адрес не входит в allowed_ips клиента
    403   context_not_allowed      контекст не разрешён клиенту либо выбор
                                   контекста запросом выключен настройкой
    404   route_not_found          нет такого эндпоинта
    404   not_found                объект не найден
    405   method_not_allowed       метод не поддерживается эндпоинтом
    429   rate_limited             превышен лимит запросов в минуту
    500   internal_error           внутренняя ошибка (подробности — в лог MODX;
                                   в ответ они попадают только при mxapi.debug)
    503   service_disabled         API выключен настройкой mxapi.enabled

Диагностика типовых отказов:

- 404 страницей сайта вместо JSON — не сработало правило веб-сервера (шаг 2);
- token_required при верном токене — до PHP не доходит заголовок Authorization
  (шаг 2, Apache);
- insufficient_permission при выданных правах — забыто право load в политике
  namespace mxapi либо не совпадает authority роли (шаг 3);
- invalid_scope — запрошен scope, которого нет в каталоге этого сайта (шаг 6).


Системные настройки
-------------------

    mxapi.enabled                1        выключатель API (0 — 503 на все
                                          запросы)
    mxapi.route_prefix           /mxapi/v1 публичный префикс маршрутов
    mxapi.context                mgr      контекст MODX по умолчанию
    mxapi.allow_request_context  0        разрешить выбор контекста заголовком
                                          X-MxApi-Context
    mxapi.token_ttl              86400    время жизни токена, сек
    mxapi.default_limit          100      пагинация по умолчанию
    mxapi.max_limit              1000     потолок limit
    mxapi.rate_limit_per_minute  120      лимит запросов в минуту на клиента;
                                          0 — выключено
    mxapi.trusted_proxies                 адреса прокси, для которых
                                          учитывается X-Forwarded-For
    mxapi.catalog_filter         all      что показывать в каталоге и OpenAPI:
                                          all | scope | permission
    mxapi.cors_origins                    разрешённые Origin через запятую;
                                          пусто — заголовки CORS не отдаются
    mxapi.log_reads              0        писать в журнал успешные чтения
                                          (записи и ошибки пишутся всегда)
    mxapi.log_lifetime           2592000  срок хранения журнала, сек; 0 — не
                                          чистить
    mxapi.debug                  0        отдавать детали внутренних ошибок в
                                          ответе; только для отладки

Настройки конкретного сайта можно задать файлом core/config/mxapi.php — он
важнее системных настроек и едет вместе с кодом проекта. Образец с пояснениями:
core/components/mxapi/config.example.php. Там же подключаются проектные
эндпоинты, провайдеры, промежуточные обработчики и алиасы исторических
маршрутов.

Уборка протухших токенов и старых записей журнала выполняется автоматически, не
чаще раза в час. Крон не нужен.


Свои эндпоинты
--------------

Ядро mxApi не знает ни про miniShop2, ни про конкретный сайт: эндпоинты
поставляют провайдеры. Как пакету или сайту добавить свои маршруты — в
документации:

    https://docs.modx.pro/components/mxapi/providers
